## Fixture, control, transport, and ABI migration

Fixture expectation schema version 2 replaces ambiguous nullable/omitted measurements with explicit evidence states and exact decimal strings. This is a preproduction, test-fixture-only schema: no customer or persisted production record is migrated. Version 1 successful-geometry files fail validation and must be deliberately upgraded with reviewed evidence; the loader does not infer unavailable data as zero or silently reinterpret old files. The additive import-failure expectation schema starts at version 1 and carries only controlled failure/artifact outcomes; it does not migrate or reinterpret successful-geometry records, and unsupported versions fail validation. Worker control-stream schema version 2 replaces version 1 by requiring the asset manifest on `execute`; asset-transport manifest schema version 2 replaces v1 by requiring an explicit direct-resource binding shape and is distinct from request schema version 1. Old or mixed supervisor/worker binaries are intentionally incompatible and fail closed, so both signed components must be rebuilt and deployed together. Native adapter ABI version 3 replaces v2's pathname input with pointer-and-length verified bytes while retaining cancellation callback/context arguments; worker and adapter binaries must also be rebuilt together. The Linux containment checkpoint adds only a sanitized termination diagnostic and platform behavior; it does not change control/request/asset, native ABI, fixture, persisted, or customer schemas, so no data migration is required. The `GeometryWorkerExecution`, `LocalAssetRoot`, authorization context/decision, audit event, controlled derivative write, and store receipt remain preproduction in-memory APIs. There are no customer records to migrate. Durable authorization, audit, manifest, and locator schemas must start with explicit versions and migration/replay policies rather than treating these Rust layouts as storage contracts.

TASK-004 later supersedes successful fixture expectation v2 with v3, adding mandatory mesh self-intersection evidence and categorical confidence/reasons. Every committed successful expectation is deliberately upgraded and unsupported v1/v2 success files now fail validation; no worker control, asset transport, native ABI, failure-expectation, production, or customer schema changes with that fixture-only migration.

The controlled mesh result is an additive wire contract starting at schema/reference v1. It does not alter worker request schema 1, control schema 2, asset manifest schema 2, native ABI 3, or exact `geometry-snapshot-v1`. No production/customer records exist. A consumer that does not understand `geometry-mesh-snapshot-v1` fails the reference check rather than interpreting those bytes as STEP evidence; future mesh-schema changes require a new version/reference and replay decision.
