# USE-2 Persistence Foundation Validation

> **Status:** In Review
> **Last updated:** 2026-09-10
> **Related requirements:** REQ-F-015, REQ-F-016, REQ-F-032; REQ-NF-007, REQ-NF-009, REQ-NF-020; DATA-005, DATA-006, DATA-008, DATA-011, DATA-017; TEST-007, TEST-014

> **Open questions:** Authenticated identity/roles and a reviewed shipped allow configuration, protected-storage policy, later aggregate migrations, and three-OS evidence

## Evidence boundary

This checkpoint establishes and advances the durable USE-2 foundation. `ShopSettingsDraft` validates profile identity, positive revision, currency-compatible optional rate/pricing/resource snapshots, mutually exclusive starter-library/catalog contexts, and actor/time/reason evidence without creating numeric defaults. `ShopSettingsApplication` preserves explicit `NotConfigured` first-run state and is the desktop entry; `ShopSettingsDraftRepository` keeps persistence behind it at the application boundary. The SQLite adapter implements immutable snapshots and revisions, an append-preserving change event, one mutable optimistic-concurrency pointer, schema/hash validation on read, and historical revision lookup.

`ShopResourceCatalogDraftApplication` owns catalog creation/edit sequencing. It requires exact current settings and optional catalog expectations, rejects implicit schema-v2 starter-library migration, preserves every current child record byte-for-byte, and permits additions only as a new identity at version one in `Draft` or the next `Draft` successor for an existing identity. Callers cannot submit selection decisions. Existing decisions are retained, while any active-for-proposals decision is newly versioned back to `Reviewed` before an edited catalog is saved so proposal eligibility must be separately reauthorized. Contract v9 now maps this service through the native Settings adapter; the service and adapter do not review child records or grant calculation authority.

Desktop contract v5 preserved all five GUI-4 analysis/estimate commands and added only `load_shop_settings` and `save_shop_settings`. Contract v6 kept that exact seven-command set and added an optional path-free Settings starter-resource DTO. Contract v7 preserves the same seven commands and adds complete path-free read-only catalog snapshots. Contract v8 adds one separately permissioned catalog-selection activation request/result command. Contract v9 preserves those eight and adds one catalog-draft save command. Its request carries exact settings/catalog expectations, one complete bounded five-kind catalog snapshot, and a bounded reason, but no selection decisions, actor, profile, time, correlation, path, database, policy, or storage authority. The Tauri host resolves the database beneath its platform application-data directory, opens it during setup, executes storage work off the UI thread, derives actor/time/profile evidence natively, and exposes only path-free DTOs. The WebView never receives a database path or SQLite handle and currently invokes neither catalog command. First run remains visibly `not_configured`; legacy save requires rate/pricing confirmations plus actor and reason, and any included starter resource bundle requires its own draft confirmation. Reopen restores exact starter values but deliberately clears every confirmation. A catalog-backed revision loads read-only, while the legacy save request cannot express catalog mutation and the host refuses to overwrite that revision.

Schema v1 is the empty-version-0 bootstrap. Schema v2 adds immutable snapshot tables for the bounded `ShopResourceLibrary` aggregate and each typed child record, plus one immutable settings-revision reference table. Schema v3 adds immutable `ShopResourceCatalog` and `ResourceSelection` snapshots plus an exact settings-revision catalog reference while reusing the child registry. The catalog retains bounded separately versioned materials, offers, stock allowances, machines, runtimes, and exact review decisions. Schema v4 adds a separate append-only, content-minimized authorization-decision event tied by foreign keys to the exact settings, catalog, and selection versions evaluated. It records correlation, actor/time, operation, allow/deny reason, and policy identity/version—never paths or resource numeric values—and does not claim that an allowed operation later succeeded. Child and selection identity/version immutability is checked independently of the aggregate version, and unchanged evidence can be reused by later settings revisions. Schema-v1, schema-v2, and schema-v3 databases migrate forward without seeding a record or event; a real schema-v2 settings JSON payload remains readable and replayable. Every embedded migration is checksummed and recorded; a changed checksum, missing expected migration, or unknown newer schema fails closed. Every opened connection explicitly enables foreign keys, WAL, full synchronous durability, a five-second busy timeout, defensive trusted-schema behavior, an integrity check, and semantic/hash verification of every stored catalog authorization event.

Focused automated tests prove:

- a new database has no rate card, pricing policy, starter resource, catalog, selection, authorization event, or current settings row;
- validated rate/pricing drafts survive save, close, reopen, and exact historical replay;
- two independently opened writers cannot overwrite a newer current revision;
- reusing an immutable policy ID/version with different bytes is rejected without changing current state;
- consistent SQLite backups reopen current and historical revisions for both ordinary and catalog-backed settings;
- schema-v1, schema-v2, and schema-v3 databases migrate to v4 with no numeric/resource/audit defaults, a schema-v2 payload replays exactly, and an unknown newer schema or altered migration checksum is rejected;
- the host adapter returns first-run absence, appends a confirmed USD revision, rejects stale and reused-version writers, reopens the same durable values, clears confirmations on load, and preserves optional missing libraries as explicit absence;
- a complete synthetic resource bundle survives host save/reopen with material/offer/stock/machine/runtime distinctions intact, unchanged snapshots can be reused by a new settings revision, and changed child bytes under a reused child version are rejected even when the aggregate version changes;
- a reviewed synthetic catalog survives save/reopen and historical replay, exact catalog evidence can be reused, changed child or selection bytes under reused versions fail without advancing current state, and out-of-band selection-payload corruption is detected;
- a synthetic allowed activation composes the headless application with the durable audit adapter, preserves its decision through backup/reopen, and creates its immutable successor only after the audit append; exact denied retries are idempotent, changed reuse of one correlation ID fails without mutation, and semantically invalid audit evidence with a recomputed matching hash fails both audit and settings-repository open; and
- the shared contract, generated application manifest, exact main-window permissions, and Tauri handler contain the same nine-command allowlist, while the WebView invokes neither catalog mutation command;
- a contract-v8 request cannot carry actor/profile/time/correlation/path/storage authority, ordinary startup returns exact native-identity unavailability without mutation, a controlled native actor under shipped deny-all is audited and denied without mutation, and a controlled matching exact-operator composition derives actor/time/correlation natively before creating and reopening the immutable successor.
- the catalog-draft service creates a first immutable catalog with no selection or numeric defaults; exact current catalog expectations are mandatory; new reviewed records, missing current evidence, and a new identity that skips version one fail without mutation; and editing a catalog with an active selection preserves its evidence as a newly versioned Reviewed decision before save; and
- the contract-v9 request cannot supply selections or host evidence, ordinary startup returns native-identity unavailability, a controlled native save maps all five record kinds and reopens the exact path-free successor, equivalent persisted decimal normalization preserves immutable source evidence, changed record content under a reused version fails without mutation, and an over-limit collection is rejected before record mapping.

Separate domain tests prove exact multi-entry round-trip, the single active-for-proposals ceiling, per-kind record bounds, duplicate identity/version rejection, reviewed-child requirements, and fail-closed selection/reference deserialization. Contract-v7 and desktop-host tests prove the complete catalog maps into typed path-free read-only DTOs, the save request has no catalog mutation field, and catalog-backed settings cannot be overwritten through the legacy save path. The GUI presents catalog identity/version, counts, and the exact active-for-proposals chain and disables that legacy save action. Those storage/host/UI tests do not constitute catalog activation, proposal, or calculation evidence. All filesystem-backed database handles are explicitly dropped before the repository test helper removes its owned temporary tree, preserving Windows sharing semantics.

The headless `ShopResourceCatalogApplication` has seven focused service tests proving explicit first-run absence plus an allowed activation that creates new settings/catalog/selection versions only after decision audit, a denied activation that is audited without mutation, an allowed decision blocked by audit failure, rejection of silent reauthorization, stale settings/catalog/selection rejection before audit, and safe switching that newly versions the prior active decision back to reviewed. The policy context pins actor, time, profile, exact settings/catalog/selection versions, operation, and correlation ID without resource numeric values. The separate draft application has seven focused tests covering no-default creation, active-selection downgrade, exact settings and catalog expectations, Draft-only lifecycle, new-identity version-one enforcement, retained current evidence, and failure without repository mutation. Eighteen focused repository tests cover schemas v1–v4, immutable persistence, concurrency, replay, backup, migration, event retry/collision, and corruption. The current WebView presents the selected-record successor boundary and a persistent save/status area, but both remain disabled with an exact native-identity explanation and submit no request.

The native Settings state opens independent settings-repository connections for legacy save, catalog drafts, and activation plus the schema-v4 audit connection. Ordinary runtime startup uses a versioned deny-all `DesktopCatalogAuthorizationPolicy` and supplies no authenticated actor, so both catalog commands return `native_identity_unavailable` and the GUI invokes neither. A separately constructible exact-profile/exact-operator rule is deliberately usable only when a trusted native identity/session boundary supplies the actor. Native tests cover durable default decision replay, exact-operator mismatch/allow/reopen, activation no-identity and deny/no-mutation, host-derived activation evidence, catalog-draft no-identity, controlled save/reopen/active-selection downgrade, immutable-version rejection, and record-ceiling rejection. No environment variable, UI confirmation, WebView field, or request payload enables identity or policy. This is authorization-contract, transition-ordering, local durable-decision, native-composition, and adapter-mapping evidence; it is not authentication, role enforcement, a shop-reviewed shipped allow policy, or an enabled desktop catalog workflow.

## Not established

This does not make stored drafts automatic calculation authority or satisfy TASK-006/USE-2. The user must still review and confirm loaded rates/pricing for the current session. Contract v10 permits the lifecycle-`Draft` starter resource bundle only in the separately versioned internal developer proposal: the application reloads and pins the exact revision/library/children, recomputes from retained one-solid STEP evidence, and requires explicit per-estimate review, limitation acceptance, quantity, and reason before ephemeral adoption. This narrow bridge does not approve the Draft, mutate settings, or make it production authority. A catalog selection marked `active_for_proposals` remains proposal-eligibility evidence only. Contract v9's catalog editor still has no enabled WebView mutation or authenticated identity source. Enabled validated successor fields, dirty-state/discard handling, catalog activation UI, authenticated identity and role membership, a shop-reviewed shipped allow policy, governed catalog-to-estimate adoption, standard stock/availability, detailed route/runtime, estimate/model persistence, document blobs, crash/power-loss recovery, broader corruption fixtures, retention/disposition, encryption/key management, protected-storage threat review, and three-OS backup/package evidence remain open. The local database is not an externally tamper-evident security log.
