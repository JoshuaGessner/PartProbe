# Persistence Architecture

> **Status:** In Review  
> **Last updated:** 2026-09-10
> **Related requirements:** REQ-F-001, REQ-F-010–REQ-F-012; REQ-NF-002, REQ-NF-007, REQ-NF-009  
> **Related ADRs:** ADR-0006  
> **Open questions:** OQ-021, OQ-022  
> **Dependencies:** SQLite/repository spike  
> **Supersedes:** None

Standalone uses one local SQLite database plus content-addressed local document storage. SQLite provides transactional local persistence; foreign keys must be explicitly enabled on every connection per the [SQLite documentation](https://sqlite.org/foreignkeys.html). Backups must treat the database and any WAL state correctly; SQLite warns the WAL is persistent state that must remain with its database when copied ([WAL documentation](https://sqlite.org/wal.html)).

## Rules

- Application services own transactions through repository/unit-of-work ports.
- Migrations are ordered, checksummed, forward-tested, and restore-tested from supported prior versions.
- Published/audit records are append-preserving; mutable drafts use optimistic concurrency.
- Attachments are staged, hashed, fsynced according to platform policy, atomically manifested, and integrity-checked on open/backup.
- `PRAGMA foreign_keys=ON`, integrity checks, busy policy, journal mode, and durability settings are explicit and tested.
- Never open a database from another trust domain without defensive treatment; see SQLite's [defensive guidance](https://sqlite.org/security.html).

Team/LAN mode uses a service and central database/object store behind the same application ports. It must not place the standalone SQLite file on a shared network filesystem.

## Current implementation boundary

TASK-003 implements only the persistence-neutral controlled-derivative port and application handoff. The in-memory write contract independently verifies immutable bytes and retains lineage, classification, exact access/retention policy references, authorization correlation, actor/time, schema/media type, integrity state, and an opaque adapter locator. It is not a durable schema and does not prove atomicity, fsync behavior, encryption, integrity-on-open, backup/restore, concurrency, or retention/disposition enforcement.

USE-2 now begins TASK-006 with a bounded SQLite adapter for immutable shop-settings drafts. Schema v1 persists validated `RateCard` and `PricingPolicy` snapshots, immutable settings revisions and change events, plus one optimistic-concurrency current pointer behind an application repository port. Schema v2 adds immutable, hash-bound snapshots for each material/offer/stock/machine/runtime child record, the bounded `ShopResourceLibrary` aggregate, and its exact settings-revision reference. Schema v3 adds immutable `shop-resource-catalog-v1` aggregate and selection snapshots plus exact settings references, reusing the child-record registry. Schema v4 adds content-minimized authorization-decision events tied by foreign keys to exact settings/catalog/selection versions. Events carry only correlation, actor/time, operation, allow/deny reason, and policy identity/version; no resource numeric values or paths are stored. No-update/no-delete triggers and normalized hashes are checked on open, exact correlation retries are idempotent, and changed correlation reuse fails. This prevents a changed child or selection from reusing its identity/version through a newly versioned aggregate, while unchanged snapshots can be reused by later settings revisions. Schema-v1, schema-v2, and schema-v3 databases migrate forward without inserting resource, numeric, or audit rows; prior settings payloads remain readable and replayable. Migration SQL is ordered and checksummed; foreign keys, WAL, full synchronous durability, a bounded busy timeout, defensive trusted-schema configuration, integrity-on-open, consistent backup, save/reopen, historical replay, and stale-writer rejection are executable evidence. A new database contains no rate, policy, resource, catalog, selection, authorization-event, or numeric seed rows.

This is a preproduction persistence foundation, not automatic calculation authority and not TASK-006 completion. Desktop contract v7 loads/saves the USD rate/pricing draft plus the optional starter resource bundle through `ShopSettingsApplication` and loads schema-v3 catalogs through complete typed path-free read-only snapshots. Contract v8 adds one host-evidence activation request/result command, and contract v9 adds one complete bounded catalog-draft save request without changing schema v4. The Tauri host owns the application-data directory and SQLite lifecycle, and the WebView receives no path or database authority. Reopened rate/pricing values clear session confirmations, and reopened starter-resource values clear their draft confirmation. Catalog fields are absent from the legacy save request; the UI disables and the host rejects that save path for catalog-backed revisions, preventing silent downgrade or overwrite. `ShopResourceCatalogDraftApplication` governs immutable catalog creation/editing through the same repository port with exact expectations, append-only record evidence, Draft/version lifecycle checks, and application-owned selection preservation/downgrade. The contract-v9 native adapter supplies actor/time/profile evidence, maps all five bounded record kinds, and preserves matching immutable source evidence; it rejects implicit starter-library migration and changed content under reused versions. A separate `ShopResourceCatalogApplication` governs the immutable transition from reviewed to active-for-proposals: it checks exact versions, evaluates policy, requires decision audit, and advances through the repository port. Schema v4 supplies a durable SQLite implementation of that audit port. Native Settings composes independent repository/audit connections with a versioned policy adapter; ordinary startup has no authenticated actor and retains deny-all, while controlled exact-profile/exact-operator tests prove mismatch denial and durable allow/reopen behavior. Neither catalog request can supply host identity/time authority, and the WebView invokes neither. A committed allowed decision records authorization—not proof that the subsequent operation succeeded. Authentication/roles, a shop-reviewed shipped allow configuration, broader access control and external tamper protection, the governed catalog editor, activation UI, model/estimate persistence, attachments, retention/disposition, encryption/key management, crash-recovery fixtures, three-OS backup evidence, and content-store atomicity remain open. Unknown newer versions, altered migration checksums, or changed event payloads fail closed.
